# Слой входа: схема

Две диаграммы. Первая отвечает на вопрос задания «клиент → шлюз / BFF → сервисы». Вторая показывает то, что на статической схеме не видно: ответ формируется в два приёма, и отказ одного источника не отменяет остальные.

Решения, которые здесь нарисованы, разобраны в [entry-layer.md](../entry-layer.md) и записаны в [ADR-0009](../adr/0009-entry-layer-ingress-and-bff.md). Состав клиентов — [clients-and-scenarios.md](../clients-and-scenarios.md).

## Клиент → слой входа → сервисы

```mermaid
graph TB
    B["Браузер<br/>SPA, десктоп, VPN"]

    B --> I["Ingress<br/>сквозные политики"]
    I --> F["BFF<br/>агрегация и домен"]

    F --> T["Тикетница"]
    F --> AU["Аудит"]
    F --> C["Кэш"]
    F --> O["Заказы"]
    F --> FL["Рейсы"]
    F --> P["Пассажиры / услуги"]
    F <--> CH["Чат-сервис (ФОС)"]
    F --> ID["SSO / OIDC"]
    CH -->|"новое обращение<br/>/internal/feedback/*"| I

    I -.-> B
    T -.-> AU
    T -.-> SL["Slack / email"]
    T -.-> FL

    classDef client fill:#08427b,stroke:#052e56,color:#ffffff;
    classDef entry fill:#1168bd,stroke:#0b4884,color:#ffffff;
    classDef svc fill:#438dd5,stroke:#2e6295,color:#ffffff;

    class O,FL,P,CH,ID,SL ext
```

Отдельного API Gateway на схеме нет — его функции выполняет ingress. Клиент один, upstream один, маршрутизировать между ними нечего; отдельное приложение добавило бы сетевой хоп и точку отказа без компенсирующего выигрыша.

Граница между двумя синими узлами проходит по знанию домена. На ingress — то, что одинаково для любого запроса: TLS, допуск из корпоративного VPN, раздача статики, роутинг `/` и `/api/*`, лимиты, старт correlation-id. В BFF — то, для чего нужно знать пользователя и предметную область: валидация сессии, роли и полевое маскирование ПДн, агрегация контекста в единую модель, таймауты и деградация. Подробная таблица — в [entry-layer.md](../entry-layer.md#граница-ответственности).

Стрелка от браузера одна, потому что SPA и API размещены на одном origin: статика и `/api/*` приезжают с одного хоста, и CORS не требуется.

Пунктир — пути, не проходящие через слой входа: раздача статики завершается на ingress; события аудита от тикетницы, SLA-алерты в Slack и фоновый запрос тикетницы к сервису рейсов для пересчёта дедлайнов идут в обход. Это важно зафиксировать, потому что у аудита два писателя, и только один из них — BFF. Извне внутрь ведут два маршрута, и оба через слой входа: браузер → ingress → BFF для пользователей и сервис обратной связи → ingress → BFF для новых обращений. Второй пускается из внутренней сети компании, а не из VPN, и подтверждается токеном сервиса ([ADR-0012](../adr/0012-inbound-call-for-new-conversations.md)).

Четыре внешних источника нарисованы отдельными стрелками намеренно: к каждому идёт свой пул соединений со своим таймаутом и circuit breaker. Это условие, при котором один BFF остаётся работоспособным — медленный источник исчерпывает собственный пул, не затрагивая остальные пути.

## Зум: как собирается карточка тикета

На схеме выше карточка выглядит как один запрос к BFF — так и есть, но за ним стоит параллельный веер по источникам с разной надёжностью. Развёртка по времени показывает, как одновременно удерживаются бюджет ≤ 2 с ([S3](../utility-tree.md)), изоляция отказов ([S6](../utility-tree.md)) и маскирование ПДн ([S8](../utility-tree.md)).

```mermaid
sequenceDiagram
    autonumber
    participant B as Браузер
    participant I as Ingress
    participant F as BFF
    participant C as Кэш
    participant T as Тикетница
    participant CH as ФОС
    participant A as Аудит

    B->>I: GET /api/tickets/{id}
    I->>F: TLS, VPN, лимиты, correlation-id
    F->>F: валидация сессии, разбор ролей

    par Тикет и лента — своё
        F->>T: тикет, сроки, заметки, системные события
        T-->>F: данные тикета
    and Вкладка по умолчанию — кэш
        F->>C: кэшируемые поля
        C-->>F: данные
    and Сообщения клиента — внешний источник
        F->>CH: первая страница переписки
        CH--xF: таймаут 800 мс, брейкер разомкнут
    end

    F->>F: маскирование полей без прав
    F->>A: событие «просмотр ПДн»
    F-->>B: ядро ≤ 2 с (p95),<br/>переписка — «нет данных»

    Note over B: вкладки запрашивают данные<br/>при открытии

    B->>F: GET /api/tickets/{id}/flight-status
    F-->>B: живой статус рейса — своя мера ≤ 4 с
```

Все обращения внутри ручки идут **параллельно**, поэтому время ответа определяется самым долгим источником, а не суммой. Именно этот факт позволяет держать ленту в общем ответе: при типичных 50–200 мс у чат-сервиса объединение не стоит ничего, а при его отказе цена ограничена таймаутом в 800 мс — вчетверо внутри бюджета ([ADR 0010](../adr/0010-single-endpoint-per-card.md)).

Маскирование выполняется до формирования ответа: значения без прав не покидают BFF, а не скрываются в интерфейсе ([ADR 0004](../adr/0004-permissions-in-shared.md)). Запись в аудит не блокирует ответ — доставка best-effort, критична неизменяемость записанного ([S10](../utility-tree.md)).

Живой статус рейса вынесен отдельно не потому, что медленный, а потому что у него **другое обязательство по времени**: мера полноты ≤ 4 с. В ответе с бюджетом 2 с его пришлось бы обрывать там, где данные были бы получены позже.
