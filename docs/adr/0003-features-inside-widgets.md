# 0003. Фичи по умолчанию живут внутри виджетов

- **Status:** Accepted
- **Date:** 2026-08-14
- **Deciders:** Лев Каплунов (архитектор сервиса)

## Context

Канонический FSD предполагает, что пользовательские сценарии выносятся в отдельный слой `features`. Инвентаризация сценариев админки саппорта показала другую картину. Рамку задают:

- **D1** — сценариев много (отмена, возврат и изменение заказа, отправка сообщения клиенту, эскалация, смена статуса, закрытие тикета), но у **большинства ровно один потребитель**: отмена заказа нужна только в `order-actions`, отправка сообщения — только в `chat`, эскалация — только в `ticket-header`.
- **D2** — в FSD **срезы одного слоя не видят друг друга**. Фича, положенная внутрь виджета, доступна ровно этому виджету: `widgets/chat` не может импортировать из `widgets/order-actions`.
- **D3** — команда 3–6 человек. Каждый срез в `features` стоит папки, public API и сопровождения; двадцать срезов-однодневок — это налог на каждую навигацию по коду.

Что рассматривал:

1. **Канонически** — все сценарии в `features`, независимо от числа потребителей.
2. **Всё внутри виджетов** — слоя `features` нет вовсе.
3. **Критерий по числу потребителей** — вынос только тогда, когда он что-то даёт.

## Decision

Беру вариант 3 — **вынос по числу потребителей**.

Фича размещается в слое `features` только если потребляется из **двух и более виджетов**. Остальные сценарии живут внутри своего виджета.

Под критерий сейчас проходят две фичи, обе нужны и в очереди, и в карточке:

| Фича | Потребители |
|---|---|
| `assign-ticket` | `tickets-queue`, `ticket-header` |
| `change-ticket-priority` | `tickets-queue`, `ticket-header` |

Сетевые вызовы во всех случаях остаются в `entities/*/api` — фичи тонкие, поэтому `close-ticket` и `change-ticket-status` переиспользуют один вызов, не дублируя его.

Правило фиксируется в README репозитория: без записанного критерия следующий разработчик разложит сценарии по канону, и разметка расползётся.

## Consequences

**Что выигрываю.** Нет слоя из двух десятков срезов, каждый со своим `index.ts`, ради сценариев с единственным потребителем (D1, D3). Критерий выноса проверяемый — число потребителей, а не вкус ревьюера. Виджет остаётся самодостаточным: всё, что нужно для его работы, лежит внутри него.

**Чем плачу.** Слой `features` выглядит непривычно пустым — читающий код должен знать правило, иначе решит, что автор не разобрался в слоях. При появлении второго потребителя фичу нужно **вынести** из виджета, и этот момент легко пропустить.

Смягчается тем же правилом D2, которое породило решение: «просто заимпортировать из соседнего виджета» физически невозможно — импорт вбок запрещён и ловится линтером. То есть FSD сам подсказывает момент рефакторинга вместо того, чтобы позволить границам размыться.

**Что отверг.** Канонический вариант — даёт единообразие, но платит двумя десятками срезов ради сценариев, которые никто не переиспользует. Вариант «вообще без `features`» — ломается на первой же фиче с двумя потребителями: её некуда положить, кроме как продублировать.
