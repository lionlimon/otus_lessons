# 0007. Единый репозиторий фронтенда, без микрофронтендов

- **Status:** Accepted
- **Date:** 2026-08-14
- **Deciders:** Лев Каплунов (архитектор сервиса)

## Context

Формулировка «monorepo или microfrontend» смешивает два независимых вопроса: **monorepo** — где физически лежит код, **microfrontend** — как приложение собирается **в рантайме**. Оси ортогональны, решать нужно обе.

Рамку задают:

- **D1** — масштаб разработки: **одна фронтенд-команда 3–6 человек, один релизный цикл**. Микрофронтенды покупают ровно одну вещь — независимый деплой независимыми командами. Это решение организационной проблемы, которой здесь нет: согласовывать релиз не с кем.
- **D2** — изоляция загрузки уже достигнута **code splitting** ([ADR 0005](0005-csr-over-ssr.md)): админка не попадает в бандл агента вообще. Техническая цель, ради которой обычно берут MFE, закрыта дешевле.
- **D3** — [S5](../utility-tree.md) требует 99.9% и запрещает деградацию в пики. Рантайм-загрузка удалённых модулей — это дополнительный класс отказов: host не смог подтянуть remote → часть приложения не открылась.

Единственный правдоподобный кандидат на выделение — `/manage/*`: другой пользователь (администратор), другая частота использования, потенциально независимый цикл изменений.

Что рассматривал:

1. **Микрофронтенды** (Module Federation) с выделением админки в отдельно деплоящийся remote.
2. **Единый репозиторий, одно приложение** — модульность через границы FSD.

## Decision

Беру вариант 2 — **один репозиторий, содержащий только фронтенд, одно приложение, один деплой**.

Модульность обеспечивается границами FSD с проверкой линтером ([ADR 0003](0003-features-inside-widgets.md)), изоляция загрузки — разбиением бандла по маршрутам.

Формулировка, по которой решал: **всё, что микрофронтенды дают технически, уже даёт code splitting; всё, что они дают организационно, при одной команде не нужно** (D1, D2).

Слово «монорепо» здесь употреблять некорректно: пакет один, это просто репозиторий приложения. BFF и сервисы живут в собственных репозиториях.

## Consequences

**Что выигрываю.** Нет рантайм-федерации — нет соответствующего класса отказов (D3). Сквозная проверка типов по всему коду: несовместимость ловится на сборке, а не у агента в браузере. Одна сборка, один артефакт, тривиальный откат переключением указателя ([ADR 0008](0008-atomic-deploy-and-rollback.md)). Для команды из 3–6 человек отсутствует накладная стоимость координации между репозиториями и версиями.

**Чем плачу.** При росте до нескольких команд с разными релизными циклами упрёмся в очередь релизов: любое изменение проходит через общий пайплайн.

Отдельное следствие раздельного хранения фронтенда и BFF: **контракт между ними пересекает границу репозиториев**. Изменение API и его потребления невозможно выкатить одним коммитом, а рассогласование проявится в рантайме. Смягчается генерацией типов из OpenAPI-схемы BFF на этапе CI — тогда ломается сборка фронтенда, а не продакшен.

**Что отверг.** Микрофронтенды — дали бы независимый деплой, но платой стали бы: рантайм-загрузка remote как точка отказа против [S5](../utility-tree.md); версионирование контрактов между host и remote, не проверяемое компилятором; дубли зависимостей либо тонкая настройка shared-scope; усложнение разбора инцидентов — чтобы восстановить картину, нужно знать, какие версии remote были загружены в конкретной вкладке.

**Условие пересмотра.** К микрофронтендам возвращаемся при появлении второй команды с собственным релизным циклом, при необходимости встроить часть UI в чужой продукт, либо если админка станет самостоятельным продуктом с отдельным владельцем.
