# 0009. Слой входа: ingress и один BFF, без отдельного API Gateway

- **Status:** Accepted
- **Date:** 2026-09-18
- **Deciders:** Лев Каплунов (архитектор сервиса)

## Context

Требуется определить, через какие компоненты внешний трафик попадает в систему и как между ними распределена ответственность. Рамку задают четыре драйвера:

- **D1 — один класс клиентов.** Снаружи в систему обращается единственное приложение: веб-интерфейс саппорта. Мобильного клиента, партнёрского API и внешних потребителей данных тикетницы нет ([Клиенты и их сценарии](../clients-and-scenarios.md)). Три роли — агент, супервайзор, администратор — используют одно приложение и один контракт; различие между ними в области видимости и весе выборки, а не в структуре ответа.
- **D2 — карточка тикета собирается из четырёх источников.** Тикетница, заказы, рейсы, пассажиры, с разной политикой свежести: ядро из кэша, статус и время вылета — только live ([TO-1](../tradeoffs.md)). Бюджет ядра ≤ 2 с p95 при очереди 10 000+ ([S3](../utility-tree.md)), отказ источника не должен приводить к недоступности карточки ([S6](../utility-tree.md)), разнородные форматы приводятся к единой модели ([S15](../utility-tree.md)).
- **D3 — доступ к ПДн разграничен на уровне полей.** Чувствительные значения не должны покидать периметр для роли без соответствующего права ([S8](../utility-tree.md)), а факт просмотра записывается в append-only журнал ([S10](../utility-tree.md)). Фронтенд механизмом защиты не является ([ADR-0004](0004-permissions-in-shared.md)).
- **D4 — доступность 99.9% при бюджете 43 минуты простоя в месяц** ([S5](../utility-tree.md)) и требование атомарного деплоя с откатом ([ADR-0008](0008-atomic-deploy-and-rollback.md)).

Рассмотренные варианты:

1. **Без слоя входа** — браузер обращается к сервисам напрямую.
2. **Только шлюз** — коробочный API Gateway перед сервисами, агрегация отсутствует либо реализуется на нём.
3. **Шлюз и BFF** — два отдельных контейнера: тонкий шлюз на периметре, за ним BFF.
4. **Ingress и один BFF** — сквозные политики на ingress-контроллере, доменная логика в единственном BFF.
5. **Ingress и несколько BFF** — по одному BFF на роль.

## Decision

Принимается **вариант 4: ingress-контроллер и один BFF**. Отдельный API Gateway как контейнер не выделяется.

BFF заводится **под класс клиента** — не под сервис и не под экран. Класс клиента один (D1), следовательно BFF один, разворачиваемый **не менее чем в двух репликах**.

Граница проходит по признаку знания домена: **на входе размещается то, что одинаково для всех запросов; в BFF — то, что требует знания предметной области и пользователя.**

| Ingress | BFF |
|---|---|
| TLS-терминация | валидация сессии, отказ анониму ([S11](../utility-tree.md)) |
| допуск только из корпоративного VPN | авторизация по ролям, полевое маскирование ПДн (D3) |
| раздача статики SPA | агрегация контекста, единая модель (D2) |
| роутинг `/` → статика, `/api/*` → BFF | таймауты, circuit breaker, деградация до «нет данных» |
| rate limiting | проксирование переписки к ФОС ([S14](../utility-tree.md)) |
| старт correlation-id | запись событий в аудит и чтение журнала (D3) |

SPA и API размещаются на одном origin, поэтому CORS не требуется.

Определяющий аргумент — не количество клиентов, а **принадлежность контракта**:

> Компонент, контракт которого меняется вместе с экранами, является BFF независимо от числа потребителей.

Единственный экран этого класса требует агрегации из четырёх источников с разной политикой свежести, полевого маскирования и изоляции отказов (D2, D3). Ни одно из этого не описывается конфигурацией шлюза — это код, оперирующий доменными понятиями. Отдельный же шлюз перед единственным upstream не имеет задач: маршрутизировать не между чем, а сетевой хоп и точка отказа расходуют бюджеты D2 и D4.

**Условие работоспособности.** Единственный слой входа означает общие ресурсы для всех путей. Опрос дёшев (маркер изменений, единицы миллисекунд), агрегация карточки дорога и зависит от самого медленного источника. По закону Литтла — `одновременных запросов = rps × время ответа` — деградация источника с 300 мс до 10 с увеличивает число одновременных запросов на порядок, и при общем пуле это затрагивает опрос, от которого зависит [S1](../utility-tree.md). Поэтому решение принимается вместе с **bulkhead**: отдельный пул соединений на каждого внешнего провайдера, фиксированный таймаут, circuit breaker и выделенный пул для poll-эндпоинтов.

## Consequences

**Что выигрываю.** Клиент не знает внутренней топологии: добавление источника или изменение чужого контракта не выходит за пределы BFF ([S14](../utility-tree.md), [S15](../utility-tree.md)). Экран собирается одним обращением вместо четырёх, а бюджет ≤ 2 с удерживается за счёт кэширования ядра при live-чтении критичных полей (D2). Данные без прав не покидают периметр, и число компонентов, касающихся ПДн, не растёт — поверхность для аудита по [S9](../utility-tree.md) остаётся прежней (D3). Деградация обрабатывается в одном месте, а не в каждом виджете. Отсутствие лишнего компонента на периметре сохраняет бюджет простоя (D4).

**Чем плачу.** BFF становится единственным путём внутрь: его отказ означает недоступность системы. Компенсируется stateless-исполнением и не менее чем двумя репликами; при rolling update система какое-то время работает на одной реплике, и этот риск принят как соответствующий целевым 99.9%. Второе — контракт BFF меняется вместе с экранами, то есть фронтенд и BFF связаны темпом релизов; при одной команде это приемлемо. Третье — постоянное сопротивление накоплению в BFF логики, которой место в доменных сервисах.

**Что отверг.**

- **Вариант 1 (без слоя входа).** Браузер оказался бы связан с контрактами четырёх внешних команд, а маскирование ПДн стало бы невыполнимым: скрытие в интерфейсе не является защитой (D3).
- **Вариант 2 (только шлюз).** Коробочный шлюз не выполняет агрегацию и маскирование — их нельзя описать конфигурацией. Реализация этой логики на шлюзе превращает его в BFF, названный другим словом, и одновременно лишает возможности взять готовое решение.
- **Вариант 3 (шлюз и BFF).** Отклонён при одном клиенте и одном upstream: маршрутизировать не между чем, а хоп и точка отказа оплачиваются из бюджетов D2 и D4. Вариант становится оправданным при появлении второго класса клиентов.
- **Вариант 5 (несколько BFF по ролям).** Различие между ролями лежит в области видимости и весе выборки, а не в структуре ответа (D1). Разделение контракта по признаку фильтра дало бы почти идентичные сервисы с дублированием изменений. Вес супервайзорской выборки приходится на БД тикетницы и обрабатывается на её уровне.
- **Вынесение API на отдельный субдомен.** Оправдано при раздаче статики через CDN, разных владельцах фронтенда и API или публичном контракте для внешних потребителей — ни одно условие не выполняется. Издержки при этом измеримы: preflight на каждом обращении при постоянном опросе ([ADR-0006](0006-polling-over-push.md)) и расширение сессионной куки до `Domain=.<зона>`, то есть на все субдомены зоны.

**Условие пересмотра.** Решение теряет силу при появлении второго класса клиентов — мобильного приложения или партнёрского API. В этом случае оправданным становится вариант 3: шлюз перед несколькими BFF, поскольку появляются маршрутизация и общие политики, дублирование которых нецелесообразно. Второй признак — вынос части ответственности BFF в самостоятельные сервисы, после которого upstream перестаёт быть единственным.
