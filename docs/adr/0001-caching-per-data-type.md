# 0001. Кэширование контекста тикета по типу данных

- **Status:** Accepted
- **Date:** 2026-07-21
- **Deciders:** Лев Каплунов (архитектор сервиса)

## Context

Карточку тикета собирает BFF: он агрегирует контекст из нескольких внешних продуктовых сервисов (заказы, рейсы, пассажиры/услуги) и отдаёт агенту единую картину. Рамку задают три вещи:

- **D1** — карточка должна открываться быстро даже в пик: **≤ 2 с (p95)** при очереди 10 000+ тикетов (сценарий [S3](../utility-tree.md)). Собрать данные из нескольких источников за это время под нагрузкой без кэша практически нереально.
- **D2** — часть данных **критична ко времени**: статус и время вылета меняются в реальном времени, особенно в «ковёр». Устаревшее значение здесь означает, что агент дал клиенту неверную информацию и тот опоздал на рейс — прямое попадание в главный бизнес-риск.
- **D3** — остальной контекст (имя пассажира, номер паспорта, история заказа) меняется редко, и цена его устаревания низкая.

Кэш ускоряет (за D1), но рискует показать устаревшее значение (против D2). Живое чтение всегда свежее (за D2), но медленное (против D1). Глобальный выбор «кэшировать или нет» проигрывает в любом случае.

Что рассматривал:

1. **Кэшировать всё** одинаково с общим TTL. Быстро (D1), но критичные к времени поля протухают — недопустимо по D2.
2. **Не кэшировать ничего**, всё читать live. Всегда свежо (D2), но не держит ≤ 2 с под пиком (против D1).
3. **Кэшировать по типу данных**: решение принимается не глобально, а для каждого поля по осям «волатильность × цена ошибки».

## Decision

Беру вариант 3 — **кэширование по типу данных**.

Контекст тикета классифицируется по двум осям — как часто значение меняется и насколько велика цена показать устаревшее:

| | Меняется редко | Меняется часто |
|---|---|---|
| **Цена ошибки низкая** | кэшировать агрессивно | кэшировать с коротким TTL |
| **Цена ошибки высокая** | кэшировать, инвалидировать по событию | **никогда не кэшировать — только live** |

Некритичные данные (D3) BFF берёт из кэша (Redis). Критичные к времени поля (статус/время рейса, D2) читаются **live из источника при каждом запросе, минуя кэш**.

Чтобы live-чтение не ломало бюджет ≤ 2 с (D1), UI применяет **прогрессивный рендеринг**: карточка появляется сразу с кэшированным контекстом (метрика S3 — про готовый каркас), а критичное live-поле догружается асинхронно с локальным индикатором загрузки в своём блоке, не блокируя остальную карточку.

Развёрнутое обоснование — в [`../tradeoffs.md`](../tradeoffs.md) (TO-1).

## Consequences

**Что выигрываю.** Карточка открывается за ≤ 2 с под пиком (D1, S3) — большинство блоков из кэша. Критичное к времени поле всегда свежее (D2), потому что читается live, а не из кэша. Латентностью плачу **точечно** — только на одном критичном блоке, а не на всей карточке.

**Чем плачу.** Растёт сложность: нужна классификация каждого поля контекста по волатильности и цене ошибки, разная политика кэширования для разных данных, инвалидация по событиям для среднего тира, поблочная асинхронная загрузка в UI. Классификацию надо поддерживать: при добавлении нового источника/поля кто-то должен решить, в какую клетку матрицы оно попадает. Для среднего тира остаётся остаточный риск устаревания — смягчается информером-тултипом «данные могут быть неактуальны».

**Что отверг.** «Кэшировать всё» — протухают критичные к времени поля, бьёт в главный бизнес-риск. «Не кэшировать ничего» — не держит ≤ 2 с под пиком. Обе крайности проигрывают именно потому, что применяют одну политику к данным с разным профилем.
