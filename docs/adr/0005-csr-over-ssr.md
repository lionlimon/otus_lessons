# 0005. CSR как модель рендеринга; SSR и SSG отвергнуты

- **Status:** Accepted
- **Date:** 2026-08-14
- **Deciders:** Лев Каплунов (архитектор сервиса)

## Context

[C4 Container](../c4-container.md) фиксирует Web UI как SPA, а [TO-1](../tradeoffs.md) — прогрессивный рендеринг карточки. Решение унаследовано из ДЗ-1 и здесь проверяется на прочность: выбор модели рендеринга не должен быть выбором по умолчанию.

Рамку задают четыре факта об эксплуатации:

- **D1** — доступ только за SSO. Поисковой индексации нет, публичного трафика нет; главный аргумент в пользу SSR неприменим.
- **D2** — **холодная загрузка происходит один раз за смену.** Агент открывает вкладку утром и работает в ней восемь часов, не перезагружая документ. Даже 3–4 секунды на старте — 0.01% рабочего времени.
- **D3** — ключевой сценарий [S3](../utility-tree.md) (карточка с контекстом за ≤ 2 с, p95) реализуется **SPA-навигацией**: документ не перезагружается, узкое место — агрегация данных на BFF, а не доставка HTML.
- **D4** — [S5](../utility-tree.md) требует доступности 99.9% и запрещает деградацию в пиковые периоды; [S9](../utility-tree.md) требует, чтобы ПДн обрабатывались только на территории РФ (152-ФЗ).

Что рассматривал:

1. **SSG** — предрендер страниц на этапе сборки.
2. **SSR** — рендеринг на сервере при каждом запросе.
3. **CSR** — статические ассеты, рендеринг в браузере.

## Decision

Беру вариант 3 — **CSR**: статические ассеты плюс агрегация на BFF.

SSG отпадает на первом же вопросе: контент динамический и за авторизацией, предрендерить нечего (D1).

SSR отвергнут потому, что в этой системе он платит трижды и не покупает главного:

- **Не адресует узкое место.** Он ускоряет загрузку документа — то есть ровно то событие, которое происходит раз в смену (D2). Открытие карточки, где живёт реальная боль, идёт мимо него (D3).
- **Бьёт по [S5](../utility-tree.md).** SSR — это рантайм в продакшене: ещё один процесс перед BFF, который нужно держать живым, мониторить и деплоить. Статика такого класса отказов не имеет (D4).
- **Бьёт по [S9](../utility-tree.md).** SSR рендерит ПДн в HTML. Такой ответ нельзя кэшировать на промежуточных узлах и раздавать с edge — то есть основной выигрыш SSR всё равно недоступен, а поверхность утечки расширяется (D4).

Первичная загрузка сознательно не оптимизируется в ущерб архитектуре. Вместо этого оптимизируется SPA-навигация: разбиение бандла по маршрутам, префетч чанка карточки в idle, прогрессивный рендеринг блоков.

Бюджет метрик: LCP ≤ 3.0 с (p75, мягче стандартных 2.5 с — обосновано D2), INP ≤ 200 мс (p75, ключевая метрика: тысячи взаимодействий за смену), CLS ≤ 0.1 (p75), открытие карточки ≤ 2 с (p95, [S3](../utility-tree.md), собственный замер).

## Consequences

**Что выигрываю.** Никакого рантайма фронтенда в продакшене: ассеты раздаются как статика, деплой сводится к выкладке файлов и переключению указателя ([ADR 0008](0008-atomic-deploy-and-rollback.md)) — это прямо работает на [S5](../utility-tree.md). ПДн не попадают в HTML, вся выдача чувствительных данных остаётся под контролем BFF ([S8](../utility-tree.md), [S9](../utility-tree.md)). Прогрессивный рендеринг из [TO-1](../tradeoffs.md) реализуется естественно: каркас из кэша сразу, live-поля догружаются в своих блоках с локальными индикаторами.

**Чем плачу.** Холодная загрузка медленнее, чем при SSR — принято сознательно по D2. Без JavaScript приложение не работает вовсе; для внутренней системы с управляемым парком браузеров это не риск. Пустой HTML до загрузки бандла требует скелетона на уровне `app`, иначе агент видит белый экран.

**Что отверг.** SSR — ускоряет событие, случающееся раз в смену, ценой рантайма в проде (против [S5](../utility-tree.md)) и ПДн в HTML (против [S9](../utility-tree.md)). SSG — неприменим к динамическому контенту за авторизацией. Пересмотреть стоит, если появится публичная часть интерфейса вне SSO — тогда для неё, и только для неё, SSR или SSG обретут смысл.
