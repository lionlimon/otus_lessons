# Решение по слою входа

[Предыдущий документ](clients-and-scenarios.md) завершается тремя выводами: агрегация необходима и выполнять её должен не клиент; между браузером и источниками требуется слой со знанием домена; основанием для BFF служит форма ответа, а не количество клиентов. Настоящий документ переводит эти выводы в решение: какие компоненты стоят на входе и как между ними распределена ответственность.

Контекст — [README](../README.md), драйверы — [Utility Tree](utility-tree.md), контейнеры — [C4 Container](c4-container.md), схема — [views/entry-layer.md](views/entry-layer.md), решение — [ADR-0009](adr/0009-entry-layer-ingress-and-bff.md).

## Нужен ли BFF

Критерий: **BFF заводится под класс клиента — не под сервис и не под экран.**

Оба альтернативных основания отклонены. BFF под сервис даёт слой, который не агрегирует, а только пересылает вызовы, — это прокси, названный другим словом. BFF под экран приводит к набору почти идентичных сервисов, в которых каждое изменение модели тикета требует правок в нескольких местах.

**Класс клиента здесь один** — веб-приложение саппорта. Следовательно, BFF тоже один.

Отсюда возникает вопрос, нужен ли отдельный слой вообще: возможно, достаточно шлюза перед сервисом тикетницы. Ответ определяется требованиями единственного экрана этого класса:

- **Четыре источника на карточку** (тикетница, заказы, рейсы, пассажиры) с разной политикой свежести, распределённые между экраном по умолчанию и вкладками: ядро из кэша, статус и время вылета — только live ([TO-1](tradeoffs.md)).
- **Бюджет ≤ 2 с p95** на ядро контекста ([S3](utility-tree.md)) и терминальное состояние всех блоков за 4 с — при том, что часть источников принадлежит другим командам и их время ответа не контролируется ([ADR-0010](adr/0010-single-endpoint-per-card.md)).
- **Изоляция отказов**: недоступный источник помечается «нет данных», остальные блоки работают ([S6](utility-tree.md)).
- **Полевое маскирование ПДн** до отдачи в браузер ([S8](utility-tree.md)) и запись факта просмотра в аудит ([S10](utility-tree.md)).
- **Приведение разнородных форматов к единой модели** ([S15](utility-tree.md)).

Ни одно из перечисленного не описывается конфигурацией шлюза. Это код, оперирующий доменными понятиями: какое поле является персональными данными, какой источник допустимо отдать из кэша, что входит в ядро контекста. Контракт при этом принадлежит потребителю — добавление блока на карточку меняет форму ответа. Компонент, контракт которого меняется вместе с экранами, по определению является BFF.

Отдельно рассмотрен вариант нескольких BFF — по одному на роль. Он отклонён в [сценарии с очередью супервайзора](clients-and-scenarios.md): различие между агентом и супервайзором заключается в области видимости и весе выборки, а не в структуре ответа. Разделение контракта по признаку фильтра дало бы два почти идентичных сервиса с дублированием изменений.

## Нужен ли отдельный API Gateway

**Нет.** Отдельный шлюз как контейнер не выделяется; его функции выполняет ingress-контроллер.

Основание — отсутствие задач, которые он мог бы решать. Шлюз оправдан при нескольких разнородных потребителях и нескольких бэкендах: он маршрутизирует запросы, унифицирует политики, скрывает внутреннюю топологию. Здесь клиент один и upstream один. Отдельное приложение между ingress и BFF добавило бы сетевой хоп в бюджет [S3](utility-tree.md) и дополнительную точку отказа в бюджет [S5](utility-tree.md) — 43 минуты допустимого простоя в месяц — без компенсирующего выигрыша.

При этом ни одна функция шлюза не исчезает: для каждой определён исполнитель.

## Граница ответственности

Принцип разделения: **на входе размещается то, что одинаково для всех запросов; в BFF — то, что требует знания домена.**

| Функция | Где | Обоснование |
|---|---|---|
| TLS-терминация | ingress | первая точка приёма запроса, далее трафик идёт внутри периметра |
| Допуск только из корпоративного VPN | ingress | сетевой периметр, не связан с личностью пользователя |
| Раздача статики SPA | ingress | статические ассеты, а не приложение ([ADR-0005](adr/0005-csr-over-ssr.md)) |
| Роутинг `/` → статика, `/api/*` → BFF | ingress | L7-маршрутизация между контейнерами |
| Rate limiting | ingress | ограничение должно отсекать трафик до расходования ресурсов приложения; ingress видит суммарный поток по всем репликам, отдельная реплика — только свою часть |
| Старт correlation-id | ingress | идентификатор должен быть присвоен до первого хопа, иначе часть пути не прослеживается |
| Валидация сессии, отказ анониму | BFF | BFF владеет сессией: обменивает OIDC-токен на куку и возвращает 401 с точкой редиректа ([S11](utility-tree.md)) |
| Авторизация по ролям, полевое маскирование ПДн | BFF | требует знания типа поля и прав пользователя ([S8](utility-tree.md)) |
| Агрегация контекста, приведение к единой модели | BFF | основное назначение слоя ([S15](utility-tree.md)) |
| Таймауты, circuit breaker, деградация до «нет данных» | BFF | относится к исходящим вызовам; ingress управляет входящим трафиком и не участвует в них ([S6](utility-tree.md)) |
| Проксирование переписки к ФОС | BFF | двусторонняя интеграция через адаптер ([S14](utility-tree.md)) |
| Запись событий в аудит и чтение журнала | BFF | оба пути к аудит-сервису проходят через слой входа ([S10](utility-tree.md)) |
| CORS | **не требуется** | SPA и API размещены на одном origin — см. следующий раздел |

Две позиции требуют дополнительного обоснования.

**Валидация сессии отнесена к BFF, хотя формально является сквозной.** Она одинакова для всех запросов и могла бы размещаться на входе. Однако реализация на ingress потребовала бы `oauth2-proxy` или аналога — то есть того самого отдельного компонента на периметре, от которого решение отказывается. Издержка решения: при появлении второго потребителя API аутентификацию придётся либо дублировать, либо выносить. При одном классе клиентов эта издержка приемлема.

**Маскирование ПДн отнесено к BFF, а не ко входу.** Проверка роли сама по себе может размещаться на периметре: допуск пользователя к маршруту — сквозное правило. Но [S8](utility-tree.md) требует иного: маскирование выполняется **на уровне полей**, чувствительные значения не должны покидать периметр вообще, а не только не отображаться. Для маскирования необходимо знать, что конкретное поле содержит номер паспорта, а конкретный пользователь относится к первой линии без соответствующего права. Это доменное знание, конфигурацией оно не описывается. Фронтенд механизмом защиты не является, что зафиксировано в [ADR-0004](adr/0004-permissions-in-shared.md).

## Один origin, CORS не требуется

SPA и API размещаются на одном хосте: `/` — статика, `/api/*` — BFF. Разные origin возникли бы при вынесении API на отдельный субдомен; это решение не принято.

Субдомен оправдан в трёх случаях: статика раздаётся через CDN, а API — нет; фронтенд и API принадлежат разным командам или кластерам; API становится публичным контрактом для внешних потребителей. Ни одно из условий не выполняется: пользователей несколько сотен и все находятся за корпоративным VPN, команда одна, внешних потребителей API нет.

Издержки при этом измеримы. Preflight-запрос добавляется к каждому обращению с `Content-Type: application/json`, а опрос выполняется постоянно ([ADR-0006](adr/0006-polling-over-push.md)). Кроме того, сессионную куку потребовалось бы расширить до `Domain=.<зона>`, то есть сделать доступной всем субдоменам. Для системы с выделенными требованиями к обработке ПДн это расширение поверхности атаки. Единый origin позволяет сохранить куку `httpOnly` и привязанной к одному хосту.

## Один BFF и количество реплик

«Один BFF» относится к числу сервисов и контрактов, а не к числу экземпляров.

По ёмкости запас значительный. Фоновый опрос при 500 агентах даёт около **150 rps**: уведомления с интервалом 30 с ≈ 17, очередь с интервалом 15 с ≈ 33, чат с интервалом 5 с ≈ 100 ([ADR-0006](adr/0006-polling-over-push.md); расчёт — `пользователи / интервал`). Открытие карточек добавляет единицы rps. Для одного процесса это фоновая нагрузка.

Тем не менее требуется не менее двух реплик, и не по соображениям пропускной способности:

- [S5](utility-tree.md) задаёт доступность 99.9% — бюджет 43 минуты простоя в месяц. При одной реплике каждый релиз расходует существенную часть этого бюджета.
- [ADR-0008](adr/0008-atomic-deploy-and-rollback.md) требует атомарного деплоя и отката; rolling update на одной реплике невозможен.
- Вытеснение пода или вывод ноды на обслуживание приводит к полной недоступности.

BFF выполнен stateless именно для этого ([ADR-0006](adr/0006-polling-over-push.md)): sticky sessions и шина между экземплярами не требуются, реплики взаимозаменяемы.

## Условие работоспособности решения «один BFF»

Единственный слой входа означает, что все пути используют его ресурсы. Определяющим фактором является не объём трафика, а различие в стоимости запроса.

Опрос дёшев: маркер изменений по индексу, единицы миллисекунд. Агрегация карточки дорога: четыре параллельных исходящих вызова, длительность определяется самым медленным источником. Связь между величинами задаёт закон Литтла — `одновременных запросов = rps × время ответа`. При времени ответа сервиса рейсов 300 мс агрегация удерживает единицы соединений; при деградации до 10 с число одновременных запросов возрастает на порядок. В случае общего пула ресурсов это затрагивает и опрос, от которого зависит [S1](utility-tree.md) с требованием нулевой доли пропущенных дедлайнов.

Отсюда условие, при котором решение остаётся работоспособным: **отдельный пул соединений на каждого внешнего провайдера, фиксированный таймаут, circuit breaker и выделенный пул для poll-эндпоинтов** (bulkhead). Медленный источник исчерпывает собственный пул, не затрагивая остальные. Тот же механизм обеспечивает [S6](utility-tree.md): при размыкании брейкера блок получает статус «нет данных» за предсказуемое время, остальная карточка остаётся работоспособной.

Тяжёлые выборки супервайзора в эту категорию не входят: на данном пути BFF выполняет проксирование, нагрузка приходится на БД тикетницы и обрабатывается на её уровне.

## Трафик, не проходящий через слой входа

Через вход проходит не весь трафик системы; это фиксируется явно.

- **Вызовы к внешним провайдерам** (заказы, рейсы, пассажиры, ФОС) — исходящие, инициатором всегда выступает система.
- **SLA-алерты в Slack и email** — исходящие из планировщика внутри сервиса тикетницы; ingress и BFF в этом пути не участвуют.
- **События аудита от сервиса тикетницы** — внутренний межсервисный вызов. У аудита два писателя, и только один из них — BFF.
- **Обращение тикетницы к сервису рейсов** за актуальным временем вылета для пересчёта дедлайнов ([S2](utility-tree.md)) — фоновый процесс, а не пользовательский запрос; BFF в этом пути был бы лишним хопом.

Извне внутрь ведёт единственный путь: браузер → ingress → BFF.

## Условие пересмотра

Решение теряет силу при появлении **второго класса клиентов** — мобильного приложения или партнёрского API. В этом случае отдельный шлюз перед несколькими BFF становится оправданным: появляются маршрутизация и общие политики, дублирование которых нецелесообразно. Второй признак для пересмотра — вынос части ответственности BFF в самостоятельные сервисы, после которого upstream перестаёт быть единственным.
